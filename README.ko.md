# Refund Agent Lab — 2단계

[English](README.md) | **한국어**

AI 고객지원의 잘못된 환불 제안, 서버 정책, 사람 승인·거절, 중복 실행을 실험하는 로컬 학습 앱입니다. Python + LangGraph + SQLite + Streamlit을 사용하며 API 키나 실제 결제 서비스 없이 작동합니다. 화면은 영어와 한국어를 지원합니다. 사이드바의 **Language / 언어**에서 전환할 수 있으며 기본값은 영어입니다. 가짜 모델은 두 언어의 환불 요청을 처리합니다.

## 설치와 실행

Python 3.11 이상이 필요합니다. 이번 검증 환경은 Python 3.14.3입니다. `requirements-lock.txt`는 이 환경에서 설치한 버전 목록이며, 다른 Python 버전에서는 `pyproject.toml` 기준 설치를 권장합니다.

```sh
cd refund-agent-lab
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
streamlit run app.py --server.address 127.0.0.1
```

브라우저에서 http://localhost:8501 을 여세요. 최초 실행 시 샘플 데이터가 자동 생성됩니다. 이후 재시작에서는 기존 DB를 사용합니다. 설치 때만 패키지 다운로드가 필요하며 기본 앱 동작에는 외부 API가 필요하지 않습니다.

```sh
# 전체 검증: 정책, 동시성, 체크포인트, 장애, 화면
python -m pytest -q
# 현재 환경의 정확한 패키지 버전으로 재설치할 때
python -m pip install -r requirements-lock.txt
python -m pip install -e . --no-deps
```

1단계 앱이 이미 실행 중이라면 해당 터미널에서 `Ctrl+C`로 종료한 뒤 위 실행 명령으로 다시 시작하세요. 새 업무 모듈과 자동 DB 변환을 반영하려면 서버 재시작이 필요합니다.

업무 기록은 `data/lab.sqlite3`, LangGraph 상태는 `data/checkpoints.sqlite3`에 저장합니다. `REFUND_LAB_DATA_DIR` 환경변수로 데이터 폴더를 바꿀 수 있습니다. 테스트는 임시 폴더만 사용합니다.

## 화면에서 실험하기

기본 고객은 김민지(C001)입니다. 요청 입력 후 **요청 처리**를 누르세요.

| 요청 예시 | 예상 결과 |
| --- | --- |
| `ORD-001 주문을 환불해주세요` | $49.00 가짜 환불 성공 |
| `ORD-002 주문을 환불해주세요` | 45일 전 구매이므로 차단 |
| `ORD-003 주문을 환불해주세요` | $159.00 → 승인 대기 저장, 환불 없음 |
| `ORD-004 주문을 환불해주세요` | 다른 고객 주문이므로 차단, 주문 내용 비공개 |
| `ORD-005 주문을 환불해주세요` | 이미 환불했으므로 차단 |
| `ORD-006 주문을 환불해주세요` | 정확히 $100.00 → 자동 환불 가능 |
| `환불해주세요` | 주문 번호 확인 요청, 실행 없음 |
| `ORD-001 ORD-006 환불해주세요` | 주문 번호를 하나로 특정하도록 확인 요청 |
| `ORD-001 상태를 알려주세요` | 환불 의사 확인 요청 |

- **같은 요청 다시 보내기**는 같은 요청 키로 재전송합니다. 새 실행이나 두 번째 환불을 만들지 않습니다.
- **요청 처리**를 다시 누르면 새 요청 키를 만듭니다. 같은 주문을 다시 지정해도 주문별 환불 고유 제약과 정책이 차단합니다.
- 모델을 **오류 실험**으로 선택하고 `ORD-002 상태를 알려주세요`를 보내면 모델은 잘못 환불을 제안하지만 서버는 기간 규칙으로 차단합니다. 이 모드는 의도적으로 환불 의사를 무시하는 학습용 모델입니다.
- 고객을 이준호(C002)로 바꾸면 ORD-004를 정상 처리할 수 있습니다. 이전 고객의 실행 목록은 표시되지 않습니다.
- **실험 데이터 초기화**는 모든 고객의 업무 기록을 트랜잭션으로 삭제하고 샘플을 다시 만듭니다. 과거 환불을 나타내는 ORD-005의 초기 환불 기록 한 건은 다시 생성됩니다.
- 잡힌 오류는 **실행 실패**로 표시하며 **실패한 실행 재시도**로 저장된 체크포인트에서 계속할 수 있습니다.

## 사람 승인·거절 실험

1. 김민지 고객으로 `ORD-003 주문을 환불해주세요`를 보내 **사람 승인 대기**를 만듭니다.
2. 사이드바에서 **담당자 모드 (학습용)**를 켜고 담당자를 선택합니다. 고객 선택과 담당자 선택은 별도의 세션 값입니다. 담당자 모드에서만 모든 고객의 대기 목록과 처리 이력을 보여줍니다.
3. **처리할 승인 요청**에서 주문과 고객, 요청 당시 금액을 확인합니다. **처리 메모 (선택)**를 입력할 수 있습니다.
4. **승인 후 환불**을 누르면 서버가 최신 주문을 다시 검사합니다. 유효하면 가짜 환불 한 건이 저장되고, 주문과 관련 대기 실행들이 **환불 완료**가 됩니다. 대기 목록에서 사라지고 이력에 **승인 완료**로 표시됩니다.
5. **거절**을 누르면 환불 없이 **환불 거절**로 종료합니다. 주문은 결제 상태를 유지합니다. 처리자·시각·메모·결과가 남습니다.
6. **승인 목록 새로고침**으로 다른 담당자의 처리 결과를 갱신할 수 있습니다. 오래된 화면에서 같은 버튼을 누르거나 반대 결정을 보내도 먼저 저장된 결정이 그대로 반환됩니다.

거절 실험은 **실험 데이터 초기화** 후 새 대기를 만들어 진행하세요. 한 주문의 결정은 최종이며 재심사·결정 번복은 이번 범위에 없습니다. 거절된 주문을 새 요청으로 다시 보내도 대기를 새로 열거나 자동 환불하지 않습니다.

승인 시 기한 만료, 소유자 변경, 기존 환불, 금액 변경을 감지하면 **차단됨**으로 종료하고 이유를 저장합니다. 승인 대기 중 금액이 100달러 이하로 바뀌어도 새 고객 요청으로 기존 대기를 우회할 수 없습니다. 이 조건들은 임시 DB와 고정 시계를 사용하는 테스트로 검증합니다.

### 중복 승인과 동시 처리

승인·거절 트랜잭션은 `BEGIN IMMEDIATE` 잠금 안에서 대기 행을 다시 읽습니다. `pending`일 때만 결정하고, 이미 `approved`/`rejected`/`blocked`면 기존 결과를 반환합니다. 승인과 거절이 경쟁하면 잠금 후 먼저 저장된 결정이 유지됩니다. 반복 요청은 첫 처리자의 정보와 메모를 덮어쓰지 않습니다.

승인 상태 변경, 정책 재검사 기록, 가짜 환불 행, 주문 상태, 관련 실행 상태와 사람 결정 기록을 하나의 트랜잭션으로 저장합니다. 환불의 주문별·실행별 고유 제약도 그대로 유지합니다. 중간 오류 시 전체가 롤백되어 대기가 유지되며 같은 버튼으로 다시 시도할 수 있습니다.

같은 주문에 여러 고객 요청이 대기 중이라면 승인 행은 한 건을 공유합니다. 결정 시 관련 실행 상태를 함께 갱신합니다. 실제 환불 행의 `run_id`는 최초 승인 요청을 만든 실행 ID이며, 화면에서는 주문 기준으로 그 한 건을 표시합니다.

### 기존 1단계 DB 호환

앱 시작 시 기존의 `pending`만 허용하던 승인 테이블을 트랜잭션 안에서 자동 변환합니다. 주문, 환불, 실행, 이벤트, 승인 ID는 보존합니다. 기존 대기는 원래 실행의 고객 ID와 변환 시점 주문 금액으로 승인 대상 정보를 채웁니다. 새 대기는 생성 시점의 고객 ID와 금액을 보관합니다. 새 설치나 재시작에서 초기화를 강제하지 않습니다.

## 초보자를 위한 설계 설명

### 1. 모델은 제안하고, 서버가 결정합니다

가짜 모델은 요청에서 주문 번호 하나와 환불 의사를 찾습니다. 자연어를 폭넓게 이해하는 LLM이 아니라 결정적인 규칙 기반 모형입니다. 주문 번호 누락, 여러 번호, 불명확한 의사는 실행하지 않습니다.

모델에는 고객 신원을 전달하지 않습니다. Streamlit 세션에서 선택한 고객 ID가 서비스에 전달되고 DB 실행 기록에 저장됩니다. 모델 응답에 고객 ID, 금액, 승인 정보가 들어 있어도 버립니다. 조회는 고객 ID와 주문 번호를 함께 사용해 다른 고객의 주문 내용을 모델이나 화면에 노출하지 않습니다.

서버 정책은 `refund_lab/policy.py`에 있으며, 제안 뒤와 실행 직전에 모두 적용합니다. 금액은 DB 주문의 **정수 센트**를 사용합니다. 예를 들어 $49.00은 4900입니다. 부동소수점 반올림 문제를 피합니다. 전액 환불만 지원하며 부분 환불은 범위 밖입니다.

### 2. 시간과 승인 기준

구매 시각과 현재 시각은 시간대가 포함된 UTC 시각입니다. 30일은 30×24시간이며 정확히 30일 경계까지 허용합니다. 미래 구매는 차단합니다. $100.00은 자동 처리할 수 있고 $100.01부터 사람 승인이 필요합니다.

고액 주문은 `approvals` 테이블에 `pending`으로 저장하고 주문은 `paid`로 유지합니다. 같은 주문에 대기 행이 여러 개 생기지 않습니다. 담당자가 승인하면 금액 제한만 해제됩니다. 소유권, 30일 기한, 기존 환불 여부는 다시 검사하며, 대기 생성 당시 금액과 현재 금액이 달라져도 차단합니다. 사람의 승인은 나머지 정책을 우회하는 권한이 아닙니다.

### 3. 두 번 누르거나 동시에 실행해도 한 번만 환불합니다

두 가지 중복을 따로 막습니다.

1. 같은 고객과 같은 요청 키에는 실행 행을 하나만 생성합니다. 같은 키를 다른 요청 내용이나 모델 모드로 재사용하면 거절합니다. 실행 중 재전송은 현재 `running` 상태를 반환합니다.
2. 서로 다른 요청 키여도 `refunds.order_id`의 UNIQUE 제약으로 주문당 환불은 한 건입니다. `refunds.run_id`에도 UNIQUE 제약이 있습니다.

실행 시 SQLite의 `BEGIN IMMEDIATE`로 쓰기 순서를 정합니다. 잠금을 획득한 뒤 최신 주문을 다시 조회하여 소유권, 기간, 금액, 미환불 상태를 검사합니다. 환불 행 추가, 주문 상태 변경, 실행 결과와 실행 이벤트 저장이 **하나의 트랜잭션**입니다. 도중에 실패하면 모두 롤백됩니다. 모든 값은 SQL 매개변수로 전달합니다.

이 보장은 로컬 가짜 환불에 대한 것입니다. 외부 결제사를 추가하면 결제사 측 멱등 키와 별도의 복구 설계가 필요합니다.

### 4. LangGraph는 진행 상태, 업무 DB는 사실을 기억합니다

고객 요청 흐름은 `propose → lookup → policy → execute → finalize`입니다. 정보 부족과 차단은 execute를 건너뜁니다. 승인 대기는 execute 경계에서 승인 행만 저장합니다.

사람의 처리는 별도의 LangGraph 흐름 `decide → observe`에서 실행합니다. 버튼 클릭마다 별도 `review:<UUID>` 스레드로 입력과 결과를 체크포인트에 남깁니다. 고객 요청의 대기 체크포인트를 수정하거나 모델을 다시 호출하지 않으며, 기존 1단계 체크포인트도 그대로 읽을 수 있습니다. 대기와 최종 결정의 기준은 업무 DB입니다. 같은 승인 ID의 여러 검토 흐름이 동시에 실행되어도 DB 트랜잭션이 하나의 결정을 보장합니다.

`decide`는 담당자 권한 확인·정책 재검사·결정·환불을 원자적으로 처리하고, `observe`는 관찰 도구에 결과를 전달합니다. 가짜 모델과 MCP용 `RefundTools`에는 사람 승인 API를 노출하지 않습니다. `identity.py`의 담당자 목록을 확인하는 검사는 업무 DB 경계에서도 수행합니다. 이는 실제 인증을 대신하는 로컬 역할 시뮬레이션입니다.

LangGraph의 `SqliteSaver`는 실행 ID를 `thread_id`로 사용해 노드 사이 상태를 디스크에 남깁니다. 업무 DB는 주문, 환불, 승인, 실행 및 단계별 이벤트를 보관합니다. 이벤트의 `(run_id, step)`도 고유하므로 노드를 다시 실행할 때 같은 단계가 중복 표시되지 않습니다. 이 단계 기록은 재시도 시 최신 내용으로 갱신되는 학습용 요약이며 불변 감사 로그는 아닙니다.

두 DB의 저장은 하나의 분산 트랜잭션이 아닙니다. 따라서 환불이 커밋된 뒤 체크포인트 저장 전에 실패할 수 있습니다. 실행을 재생하면 `run_id`에 이미 환불이 있는지 먼저 검사하여 기존 결과를 돌려줍니다. 이 구간을 테스트합니다. 사람 승인도 커밋 후 체크포인트 저장이 실패하면 업무 DB의 확정 결과를 반환하며, 재실행은 그 결과를 재사용합니다. 뒤늦게 끝나는 고객 요청의 finalizer는 확정된 환불·거절·차단 결과를 덮어쓸 수 없습니다. 화면의 최종 상태는 업무 DB를 기준으로 표시합니다.

```text
  adapters.py            ModelAdapter / RefundTools / Observer 인터페이스와 가짜 모델

```

- 실제 LLM: `ModelAdapter.propose()` 구현을 서비스에 주입합니다. 반환은 `action`, `order_id`, `reason`이며 모든 응답을 불신하고 검증합니다. 예외 메시지는 화면에 원문을 내보내지 않습니다.
- MCP: 향후 `RefundTools` 구현을 추가할 경계를 마련했습니다. MCP로 옮기더라도 서버의 소유권·정책·트랜잭션 검사를 거치는 실행 API를 호출해야 합니다. 모델에게 DB 쓰기 권한을 주지 않습니다.
- Langfuse: `Observer.on_step()`에 관찰 도구를 연결할 수 있습니다. 현재 기본은 아무 동작도 하지 않습니다. 관찰 도구의 장애가 환불 판단을 바꾸지 않도록 분리했습니다. 단계 payload에는 요청 관련 정보가 있으므로 외부 관찰 서비스 도입 때 데이터 최소화도 설계해야 합니다.

API 키와 비밀값은 코드에 없습니다. 외부 모델이나 관찰 서비스는 연결되어 있지 않습니다.

## 이번 단계의 경계

고객 선택은 학습용 신원 시뮬레이션이며 실제 인증이 아닙니다. 앱은 로컬에서 사용하세요. 승인·거절과 승인 시 재검사는 구현되어 있습니다. 실제 고객/담당자 인증, 재심사·결정 번복, MCP 서버, Langfuse 연결, 장애 주입 UI, 강제 종료 자동 복구 및 운영 배포는 후속 단계입니다.

잡힌 예외는 `failed`로 표시해 체크포인트 재시도를 제공합니다. 프로세스를 강제 종료하면 아직 `running`인 실행이 남을 수 있습니다. 이 상태를 자동 재할당하는 lease/작업자 복구는 이번 단계에 포함하지 않습니다. 연습을 계속하려면 실행 중 작업이 없는 상태에서 데이터 초기화를 사용하세요.

초기화는 업무 DB만 재생성하고 체크포인트 DB는 보존합니다. 새 실행은 새 UUID를 사용해 이전 체크포인트를 재사용하지 않습니다. 완전히 지우려면 앱을 종료한 뒤 `data/` 폴더를 삭제하세요. 앱 실행 도중 DB 파일을 삭제하거나 다른 사용자의 작업과 동시에 초기화하지 마세요.
